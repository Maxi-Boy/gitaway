# Решения для версии 0.1 (черновик)

Статус: черновик, правится по итогам прототипов.

## Цели (ориентиры, уточнить замером code-server на том же сервере)

- Один бинарник с вшитым фронтендом (`go:embed`), без Node.js на сервере.
- Потребление RAM в простое и размер пакета заметно меньше, чем у code-server
  (конкретные числа зафиксировать после замера).
- Быстрая первая загрузка интерфейса по локальной сети.
- Работа от имени обычного пользователя, как в терминале.

## Не делаем в v0.1

- Расширения и плагины, подсказки кода уровня LSP.
- Несколько пользователей и роли.
- Редактор конфликтов слияния (конфликтный файл открывается как обычный).
- Поддержка GitLab и других хостингов (сначала только GitHub).

## Конфигурация

Один файл (формат выбрать: TOML или YAML) со значениями по умолчанию, безопасными для запуска:

- `listen`: по умолчанию `127.0.0.1:<порт>`
- `roots`: разрешённые корни для репозиториев и локальной ФС
- `default_folder`: папка по умолчанию для серверной панели
- `keys_dir`: каталог ключей (права 0700)
- `pam_service`: имя PAM-сервиса
- `session_ttl`: время жизни сессии

## Длительные операции

В 0.1 fetch, pull и push синхронные (таймаут 60 с) под блокировкой репозитория.
С 0.2 всё долгое (clone, задачи, терминал) идёт через сеансы, см. раздел «Сеансы».

## Безопасность (основное)

- Все пути проверяются: абсолютный вид, раскрытие symlink, префикс из `roots`.
- Аргументы git передаются списком, имена веток проверяются (не начинаются с `-`).
- WebSocket: проверка Origin и сессии. Cookie: Secure, HttpOnly, SameSite.
- Ограничение попыток входа. Пароль не логируется.
- Доступ к GitHub: deploy-ключи на репозиторий; Device Flow только для мастера
  подключения, токен не сохраняется.
- Файлы ключей и конфигурации: права 0600, каталоги 0700.

## Статус реализации (скелет)

Сделано и покрыто тестами:

- `internal/config`: загрузка настроек (пока JSON), раскрытие `~`, проверка значений.
- `internal/fsx`: защита путей (корни, symlink, `..`).
- `internal/gitx`: запуск git, проверка входных данных, ветки, статус, ahead/behind,
  fetch/pull/push по отдельности, обновление неактивной ветки, worktree,
  последний коммит по элементам каталога (с кэшем).
- `internal/auth`: интерфейс проверки, режим токена, сессии, ограничение попыток входа.
- `internal/store`: реестр репозиториев (repos.json, права 0600).
- `internal/jobs`: блокировка операций по репозиторию.
- `internal/copyop`: копирование и перемещение между панелями: план (конфликты, данные для диалога),
  решения по файлам и массовые политики (replace_all, replace_newer, skip_all, keep_both_all),
  атомарная запись с сохранением времени изменения, защита путей, запрет копирования в себя и в .git.
- `internal/server`: API (вход, репозитории, ветки, статус, worktree, дерево файлов,
  коммиты, чтение и сохранение файла, операции git), CSRF, проверка Origin, заголовки безопасности.
- `web`: интерфейс на ES-модулях без сборки (`web/app/`), см. «Каркас интерфейса».

Ждёт результатов прототипов (каталог `proto/`):

- (сделано) PAM: `auth/pam.go` с тегом сборки `pam`, см. «Вход паролем (PAM)».
- Терминал (pty + WebSocket): после проверки term.
- Подход к «последнему коммиту» уже реализован в `gitx`, но может быть доработан по замерам lastcommit.

Не сделано: клонирование по URL, deploy-ключи и мастер подключения GitHub, stage и commit,
интерфейс двухпанельного режима и диалога конфликтов (бэкенд готов), настоящий интерфейс по макету,
очередь задач с потоковым выводом.

## Копирование между панелями (copyop)

- Источник и назначение описываются как `{repo, wt, path}` (рабочая папка git) или `{dir, path}`
  (обычная папка на сервере); `items` это имена выбранных элементов относительно каталога источника.
- `plan` ничего не меняет. `copy` строит план заново и без решений по всем конфликтам отвечает 409
  `unresolved_conflicts` (со списком путей), не меняя диск.
- Решения: по файлу (`decisions`: replace, skip, keep_both) или массово (`policy`). Явное решение главнее политики.
- `replace_newer` сравнивает время изменения с точностью до секунды. Время изменения при копировании сохраняется.
- Не копируются: символические ссылки, каталоги `.git`, специальные файлы. Конфликты типов
  (файл против каталога) и совпадающие целевые имена пропускаются без потери данных.
- Файл не заменяется самим собой: при совпадении источника и цели замена пропускается, перемещение ничего не удаляет.
- Дата создания берётся через `statx` (Linux amd64 и arm64); если файловая система её не хранит, поле пустое.
- Перемещение это копирование и затем удаление источника; пустые каталоги источника удаляются.
  Для рабочей папки git это изменение, которое увидит `git status`.

## Изменения: stage, commit, diff, отмена

- Пути из запроса идут после `--` с `GIT_LITERAL_PATHSPECS=1`: `*.go` и `:(top)` это имена,
  а не шаблоны. Проверка формата в `gitx.CleanPaths`, границы через Sandbox (symlink наружу 403).
- Отмена действует по списку `git status --no-renames` для выбранных путей, а не по вводу:
  отслеживаемые файлы возвращаются к HEAD (индекс и диск), новые удаляются, игнорируемые
  не трогаются. Ответ содержит список затронутых файлов.
- Коммит только из индекса (без `-a` и без amend), текст одним аргументом `--message=`.
  Хуки репозитория выполняются. Пустой индекс это 400, а не ошибка git.
- Ответы stage, unstage, discard и commit сразу содержат свежий `status`.

## Доступ по сети и версия файла

- `allow_cidrs` в конфигурации: сети и отдельные адреса. Проверка идёт первой, до входа
  и статики; чужой адрес получает 403. Loopback разрешён всегда. Пустой список: без ограничения
  (при `listen` не на loopback в лог пишется предупреждение).
- `X-Real-IP` учитывается только при `trust_proxy` и только от loopback (nginx на той же
  машине). Это же правило действует для лимита попыток входа.
- `GET /api/file` отдаёт `version` (наносекунды mtime и размер, строкой). `PUT` с `version`
  возвращает 409, если файл изменился; без `version` записывает без проверки.

## Сеансы (терминал сделан в 0.1, задачи в 0.2)

Один механизм для терминала, задач, clone и долгих операций git. Пакет `internal/session`;
API: `GET/POST/DELETE /api/sessions`, `GET /api/sessions/ws?id=` (двоичные кадры: ввод и вывод,
текстовые: `{"type":"resize"}` от клиента, `{"type":"exit","code"}` от сервера). WebSocket
требует Origin того же хоста (CSRF-заголовок в WebSocket не передаётся).

- Сеанс это процесс в pty (`creack/pty`) с рабочей папкой вкладки-ветки, кольцевым буфером
  вывода (около 2 МБ) и состоянием: идёт, завершён с кодом, остановлен.
- Подключение по WebSocket (`coder/websocket`): при подключении клиент получает буфер,
  дальше живой вывод. Закрытый браузер процесс не останавливает. Переподключиться можно
  с другого устройства.
- Остановка: SIGINT группе процессов, через 5 с SIGKILL. Таймаут задаётся у задачи.
- Оболочка: `bash -l` (или `$SHELL -l`), чтобы PATH и переменные были как при входе по SSH:
  у systemd-сервиса окружение почти пустое.
- Ограничения: число одновременных сеансов (например, 16) и время жизни завершённого
  сеанса (например, сутки), чтобы память не росла.

## Задачи и мои скрипты (0.2, сделано)

Одна модель «задача» из трёх источников; в интерфейсе один выпадающий список «▶»
(сначала последние запущенные, затем группы «Мои», «Репозиторий», «Авто»).

    {
      "name": "Бэкап сборки",
      "steps": ["make build", "tar czf ~/backup/app-{branch}-{date}.tgz bin/"],
      "cwd": "worktree",            // или абсолютный путь внутри roots
      "scope": "global",            // или id репозитория
      "confirm": false,             // спросить «Запустить?» перед запуском
      "continue_on_error": false,
      "timeout": "30m"
    }

- **Шаги** выполняются одной оболочкой по очереди, как если бы их вводили в терминале:
  `cd` и переменные сохраняются между шагами. Перед каждым шагом в вывод пишется заголовок
  «▶ 2/3: команда». По умолчанию остановка на первом ненулевом коде выхода.
- **Подстановки**: `{worktree}`, `{repo}`, `{branch}`, `{date}` (ГГГГ-ММ-ДД), `{time}` (ЧЧММСС).
  Значение подставляется в кавычках оболочки (`'...'` с экранированием), поэтому имя ветки
  не может стать командой; оборачивать подстановку в свои кавычки не нужно. Другие фигурные
  скобки (`${HOME}`, `awk '{print $1}'`, `{a,b}`) не трогаются.
- **Мои скрипты** хранятся в `data_dir/tasks.json` (0600). Это команды самого пользователя,
  подтверждение доверия не нужно.
- **Автоопределение**: цели `Makefile` (только явные цели без `%` и `.`), для `go.mod`
  build, test, vet; скрипты `package.json`; `cargo build/test`; `pytest` при наличии
  `pytest.ini`, `pyproject.toml` или `tests/`. Автоопределённые задачи предлагаются,
  но ничего не запускают сами.
- **`.gitaway.json` в репозитории** (`{"tasks": [...]}`, тот же формат без `scope`):
  запуск означает выполнение команд из чужого кода. Поэтому перед первым запуском
  показывается содержимое и вопрос «Доверять задачам этого репозитория?». Доверие
  хранится как SHA-256 файла в `data_dir/trust.json`; любое изменение файла (pull,
  переключение ветки) снова требует подтверждения.
- Ссылки из вывода: `путь:строка[:колонка]` и `File "путь", line N`; путь проверяется
  через Sandbox относительно рабочей папки, иначе ссылка не делается.

## Просмотр dev-сервера (заложено, не делаем)

Если понадобится открыть приложение, запущенное на сервере (например, порт 3000):

- Только на **отдельном origin**: `https://p3000.dev.example.com` (wildcard-поддомен в nginx)
  или отдельный порт. На том же origin JavaScript проксируемого приложения смог бы
  вызывать API gitaway с cookie пользователя.
- Вход: одноразовый токен из основного интерфейса, обмениваемый на отдельную cookie
  этого origin; cookie gitaway туда не попадает.
- Порты: только из списка в конфиге (`preview_ports`) или слушающие на loopback процессы
  этого пользователя.
- Сейчас ничего из этого не реализуется; в интерфейсе нет кнопки. Конфиг и маршруты
  с префиксом `/preview/` зарезервированы и не используются ничем другим.

## Каркас интерфейса (0.1, шаг 4)

- ES-модули без сборки: `web/app/` (маршрутизатор по `location.hash`, состояние, API-клиент
  с CSRF и повтором, компоненты), `web/app/i18n/ru.js` со всеми текстами.
- Маршрут: `#/repo/<id>/wt/<ветка>/file/<путь>:<строка>`; всё состояние экрана
  восстанавливается из адреса.
- Палитра команд: реестр `commands.register({id, title, keys, run, when})`; кнопки,
  меню и горячие клавиши вызывают команды из реестра.
- Нижняя панель: вкладки «Терминал», «Задачи», «Проблемы», «Вывод»; в 0.1 работает «Вывод»
  (результаты fetch, pull, push, commit).
- Связь: индикатор соединения, повтор GET-запросов, черновик несохранённого файла
  в `localStorage` по ключу «репозиторий + путь + version».

## Библиотеки интерфейса (web/vendor)

- CodeMirror 6 и xterm.js 6 собираются `tools/vendor/build.sh` из исходников на закреплённых
  тегах GitHub (`tools/vendor/versions.txt`) локальным esbuild; результат лежит в репозитории,
  чтобы сборка gitaway не требовала Node. Лицензии: `web/vendor/LICENSES.txt` (все MIT).
- Подсветка через `@codemirror/legacy-modes`: им не нужен генератор парсеров при сборке.
- Обе библиотеки грузятся динамическим `import()` только при открытии файла или терминала.

- Интерфейс задач (как конфигурации запуска в IDE): в верхней панели выпадающий список задач
  (группы «Мои скрипты», «Из репозитория», «Найдены в проекте»; выбор запоминается для каждого
  репозитория), кнопка «▶» запускает выбранную, кнопка «Скрипты» открывает редактор моих
  скриптов. Вкладка «Задачи» нижней панели: запуски и все задачи (на телефоне задачи там). Запуск открывает сеанс
  в терминале; значок последней задачи на вкладке ветки (▶ идёт, ✓, ✗). Повтор последней:
  Ctrl+Shift+B (F5 оставлен браузеру). Уведомление браузера только если вкладка не на экране.

## GitHub: deploy-ключи (0.2)

- Ключ ed25519 на каждый репозиторий создаётся в Go (формат OpenSSH, без ssh-keygen),
  закрытая часть `data_dir/keys/<id>` (0600, каталог 0700), описание в `data_dir/keys.json`.
  Повторный запрос для того же owner/repo отдаёт тот же ключ: его уже могли добавить на GitHub.
- Ключ хоста GitHub закреплён (ed25519, SHA256:+DiY3wvvV6TuJJhbpZisF/zLDA0zPMSvHdkr4UvCOqU)
  в своём `data_dir/known_hosts`, `StrictHostKeyChecking=yes`; `~/.ssh` пользователя не трогается.
- Проверка: `git ls-remote` по SSH на 22, при сетевой ошибке SSH через 443 (`ssh.github.com`);
  рабочий способ запоминается у ключа. Причины отказа: denied (ключ не добавлен), not_found,
  network, host_key.
- Клонирование идёт сеансом (вывод в терминале). После успеха в `.git/config` репозитория
  пишется `core.sshCommand` с ключом: fetch, pull, push работают из интерфейса и из терминала.
- Публичный репозиторий можно клонировать по HTTPS без ключа (только чтение).
- Токены GitHub не используются и не хранятся. Device Flow с автодобавлением ключа: позже.

## Вход паролем (PAM) и язык интерфейса

- PAM собирается только с тегом `pam` (cgo, нужен `pam-devel`): `make build-pam`.
  Обычная сборка остаётся без cgo, режим `pam` в ней сообщает, что не поддерживается.
- Войти можно только под пользователем, от имени которого запущен gitaway: пароль
  проверяется через PAM (auth и account), но процесс не меняет пользователя. Запуск
  в режиме pam от root запрещён.
- Сервис PAM `gitaway` (`/etc/pam.d/gitaway`, образец `packaging/pam.d-gitaway`, через
  `system-auth`). Нет файла: предупреждение при запуске (PAM возьмёт сервис `other`).
- Неверный пароль: 401, общий лимит попыток. Ошибка самого PAM (сервис не настроен): 503
  `auth_unavailable`, подробность только в лог.
- `GET /api/login` отдаёт режим входа, чтобы экран входа показал нужную подсказку.
- Язык: `ru` и `en`, словари с одинаковыми ключами (`web/app/i18n/`). Выбор хранится в браузере
  (`localStorage gitaway:lang`), без выбора берётся язык браузера (ru, kk, be, uk → русский,
  иначе английский). Переключатель на экране входа, в меню пользователя и в палитре команд;
  смена языка перезагружает страницу. Даты через `Intl` выбранного языка, время 24 часа.
- Служебные строки задач (шаг упал, готово, таймаут) сервер пишет на языке из запроса запуска.
